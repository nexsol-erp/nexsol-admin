Cold start order

These are numbered because the order is real: each step depends on the one before it. Start a Spring service before PostgreSQL is accepting connections and it will fail its migrations and crash-loop rather than wait.

  1. PostgreSQL

    Everything with a database behind it waits on this — nxserver, nxworkflow, and Keycloak's own container database.

    systemctl start postgresql@12-main.service

  2. ZooKeeper, then Kafka

    Kafka registers itself with ZooKeeper at startup and will not come up without it.

    systemctl start zookeeper.service
systemctl start kafka.service

  3. Keycloak

    Its containers carry their own Postgres and a health gate, so up -d waits for the database to be ready before starting Keycloak itself.

    cd /opt/apps/keycloak
docker-compose --env-file keycloak.env up -d

  4. The four application services

    Independent of each other — order among them does not matter.

    systemctl start nxserver.service nxconnect.service nexsol-ai.service nxworkflow.service

  5. nginx

    Last, so the site does not serve 502s while the backends are still coming up.

    systemctl start nginx.service

Cron jobs

Nothing schedules these from the operating system — there is no application entry in any crontab or /etc/cron.d. Every job below is a Spring @Scheduled method inside nxserver, so they exist only while that service is running and they restart with it.

The server clock is UTC. Every time in this section is UTC, so the "2:45 AM" sweep actually runs at 08:15 IST — insights land mid-morning, not overnight. To have them ready before the working day in India, shift the cron back by 5½ hours (0 45 20 * * * = 02:15 IST).

Cron format — six fields, not five

0     45    2     *     *     *
sec   min   hour  dom   mon   dow      -> 02:45:00 UTC every day

Changing one

# All of these live in /home/deploy/server/application.properties,
# then: systemctl restart nxserver.service

ai-branch-manager.cron=0 45 2 * * *     # the nightly default
ai-branch-manager.cron=0 */10 * * * *   # every 10 min — TESTING ONLY

Deleting the property does not switch the job off

Each cron is written ${ai-branch-manager.cron:0 45 2 * * *} — the part after the colon is a built-in default. Remove the line and the job still runs, on that default. To actually stop one: 

ai-branch-manager.enabled=false   # job fires, returns immediately — the real off switch
ai-branch-manager.cron=-          # Spring registers no trigger at all

AI training runs nightly against a tenant that is not on this server

AiTrainingScheduler holds its tenant list in code — List.of("7559004113a"). That database does exist, but it holds zero items and zero sales — it is one of roughly twenty abandoned or half-provisioned tenants on this server, against a single live one. So the job runs every night at 02:05 and trains on nothing. It has no enable flag and no cron property either, so it cannot be switched off or retargeted from configuration. Worth fixing in code rather than leaving as recurring noise.

Insights can create real work on this tenant

ai-branch-manager.workflow-creation-enabled=true is set in production, so the 02:45 sweep does not merely report — it can raise workflow tasks for tenant 9446968394a. Re-running the sweep is safe regardless: ux_ai_insight_open is a partial unique index on dedup_key WHERE status='OPEN', so a repeat cannot duplicate an open insight.

Traps

Each of these cost real debugging time on this server. They are here so they cost it once.

A green systemctl means nothing

Every unit here is Type=simple, so systemctl restart succeeds the moment the process spawns — before Spring has read a property, let alone bound a port. A service that boots and immediately crashes restarts green. Always follow a restart with the health check for that service.

PostgreSQL 12 has no gen_random_uuid()

It became core in 13. Any migration calling it fails here unless pgcrypto is installed in that database — the extension is per-database, never cluster-wide. This is why the same SQL can work on one tenant and fail on another, and it crash-looped nxworkflow on its first start. 

psql -h 127.0.0.1 -U postgres -d <database> -c 'CREATE EXTENSION IF NOT EXISTS pgcrypto;'

It fails even when the statement would touch no rows: the function is resolved when the statement is parsed, not when a row is produced.

Port 8081 is nxconnect, not a Schema Registry

No Schema Registry runs on this server. SCHEMA_REGISTRY_HOST=localhost in workflow.env resolves to localhost:8081, which is the WebSocket relay. Nothing currently exercises that path, so it is latent rather than broken — but it will not behave as anyone reading the config would expect.

KEYCLOAK_HOST does not control token validation

It feeds spring.security.oauth2…issuer-uri, which is never read — SecurityConfig declares its own JwtDecoder, so Boot's auto-configuration backs off. The effective settings are MINIFLOW_OAUTH2_ISSUER_URI and MINIFLOW_OAUTH2_JWK_SET_URI; both are set in workflow.env. Getting the issuer wrong is silent until the first login, then rejects every token.

docker compose is not a command here

Only the standalone docker-compose v2.24.2 binary is installed. The space-separated plugin form fails.

The deploy user needs a sudoers rule for CI

deploy owns /home/deploy/workflow, so the deploy's file steps need no elevation — but the restart does, and CI cannot answer a password prompt. The rule lives at /etc/sudoers.d/nxworkflow-deploy and is deliberately limited to this one unit; NOPASSWD on cp/mv would be root access for anyone who can push to the repository.

nxserver's config exists nowhere but the server

/home/deploy/server/application.properties is not in git and is not replaced by deploys. Copy it before editing. Nothing else holds these values.
